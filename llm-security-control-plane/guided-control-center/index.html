Bedrock Gateway 만들기

직접 작성

작은 Bedrock Gateway를 직접 완성합니다. Starter는 HTTP 요청은 받지만, 사용자가 요청한 512 Token을 그대로 Nova Lite에 보냅니다. 요청 형식을 검사하고 모델을 서버에서 고정한 뒤, 출력을 최대 128 Token으로 줄이도록 코드를 완성합니다. 마지막에 서버가 미리 준비한 네 가지 요청으로 정상 요청은 통과하고 잘못된 요청은 Nova Lite에 닿기 전에 멈추는지 확인합니다.

LEARNER-OWNED GATEWAY

HTTP 요청을 Nova Lite 호출로 연결하기

llm-security-control-plane/guided-labs/h01-bedrock-gateway/server.py에서 Pydantic 요청 계약과 Boto3 converse() 호출을 확인하고, 실제 전달 상한을 다음처럼 구현합니다. 이 줄은 Gateway의 요청 처리 코드 안에서 실행됩니다.

effective_max_tokens = min(request.max_output_tokens, 128)
result = boto3.client("bedrock-runtime", region_name="us-east-1").converse(
    modelId="us.amazon.nova-lite-v1:0",
    messages=[{"role": "user", "content": [{"text": request.message}]}],
    inferenceConfig={"maxTokens": effective_max_tokens, "temperature": 0.0},
)

MODEL

질문을 보내면 실제 모델 응답이 여기에 표시됩니다.

입력한 질문을 현재 H01 Gateway가 Nova Lite에 보냅니다. 화면에는 모델 답변과 Gateway가 실제로 전달한 Token 상한이 나옵니다. 자유롭게 동작을 살펴보는 기능이며 실습 통과 판정에는 사용하지 않습니다.

아직 모델을 호출하지 않았습니다.

H01 Gateway가 “OK라고만 답하기” 요청을 Nova Lite에 보냅니다. PASS가 나오면 AWS 자격 증명과 모델 연결이 정상이라는 뜻입니다. 아직 내가 작성한 Token 제한 코드가 맞다는 뜻은 아닙니다. 서버가 미리 준비한 네 가지 요청을 H01 Gateway에 보냅니다. 정상 요청은 Nova Lite까지 가야 하고, 빈 문장과 모델을 바꾸려는 요청은 Gateway에서 멈춰야 합니다. 검증기가 실제 Token 상한과 모델 호출 횟수를 대조해 HIT·PASS·ERR로 보여 줍니다.

고객지원 문서를 검색에 연결하는 앱을 만듭니다. AWS 자원은 제공 Gateway가 서버 고정 이름과 정책으로 준비하고, 수강생 앱은 문서 입력을 검증해 승인된 S3 경로와 Titan Text Embeddings V2 호출로 전달합니다.

LEARNER-OWNED DOCUMENT APP

클라이언트 경로를 버리고 서버 경로 만들기

llm-security-control-plane/guided-labs/h02-document-ingestion/server.py의 요청 계약과 prepare_document()를 작성합니다. HTTP body에 없는 경로를 서버가 실행 ID로 만들고 제공 Gateway에 전달합니다.

class DocumentRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    execution_id: str = Field(pattern=r"^[0-9a-f-]{36}$")
    started_at: str
    title: str = Field(min_length=1, max_length=120)
    body: str = Field(min_length=10, max_length=4000)
    scenario: Literal["normal", "risk"]

def prepare_document(request: DocumentRequest) -> dict:
    object_key = f"h02/knowledge/{request.execution_id}.md"
    response = httpx.post(
        f"{GATEWAY_URL}/v1/h02/documents",
        json={
            "execution_id": request.execution_id,
            "started_at": request.started_at,
            "title": request.title,
            "body": request.body,
            "object_key": object_key,
            "scenario": request.scenario,
        },
        headers={"Authorization": f"Bearer {SERVICE_AUTH_TOKEN}"},
        timeout=30.0,
    )
    response.raise_for_status()

H03 · LEARNER-OWNED SYNC APP

현재 동기화가 끝난 뒤에만 검색하기

동기화(ingestion)는 S3 원문을 Knowledge Base 검색 저장소에 반영하는 작업입니다. H03은 H02 자원을 이어 쓰지 않습니다. 전용 Knowledge Base에는 폐기 문서가 남아 있고 S3에는 현재 문서만 있는 상태에서 시작합니다. guided-labs/h03-ingestion-search/server.py의 may_retrieve()가 같은 현재 job과 COMPLETE를 모두 확인하도록 작성합니다.

def may_retrieve(current_job_id: str, observed_job_id: str, status: str) -> bool:
    same_job = hmac.compare_digest(current_job_id, observed_job_id)
    return same_job and status == "COMPLETE"

job ID는 Browser가 보내지 않고 앱이 ingestion 시작 응답에서 저장합니다. 수정한 source를 image에 넣고 H03 앱만 다시 연결합니다.

PASS는 이 시작 상태가 준비됐다는 뜻이며 H03 앱 코드가 안전하다는 뜻은 아닙니다. 서버가 S3 원문을 검색 저장소에 반영하는 현재 동기화 작업을 시작하고, 완료 전 검색과 완료 후 검색을 차례로 실행합니다. 완료 전에는 검색 호출이 없어야 하고, 완료 후에는 현재 문서의 source만 나와야 합니다. 검증기가 실제 job ID·상태·검색 source를 다시 대조해 HIT·PASS·ERR로 보여 줍니다.

관리형 Guardrail을 “따로 시험한 것”과 “실제 모델 요청에 연결한 것”은 다릅니다. H04에서는 같은 출력 이메일 정책을 먼저 단독 검사하고, Nova Lite 호출에도 연결해 모델이 만든 이메일이 Browser에 나오기 전에 바뀌는지 확인합니다.

DIALOG PATH + TOPICAL EVALUATION

정확한 연결과 안전한 답을 따로 확인하기

검증은 정확한 연락처 질문, 처음 보는 비슷한 표현, 복구 코드 요청, 지원하지 않는 요청을 차례로 보냅니다. 각 요청의 UserMessage → UserIntent → BotIntent → BotMessage event와 별도의 activated flow를 확인한 뒤 같은 설정으로 NeMo Topical 평가를 실행합니다.

NeMo 0.22.0의 이 평가는 UserIntent가 맞으면 BotIntent와 BotMessage도 맞다고 가정합니다. 따라서 0/0/0은 보류한 한국어 문장의 UserIntent 분류가 맞고 bot 오류 counter가 늘지 않았다는 뜻일 뿐, 실제 답을 확인한 안전 점수는 아닙니다. 실제 BotIntent·BotMessage와 합성 marker는 별도의 고정 네 요청이 판정합니다.

서버가 고정한 한국어 요청 네 개를 현재 H05 Dialog Rail에 보내 intent·flow·BotMessage를 기록한 뒤, 같은 설정으로 NeMo Topical 평가를 실행합니다. 검증기는 새 영수증과 평가 결과를 다시 확인해 정상 연락처는 유지되고 복구 코드 marker는 사라졌는지 HIT·PASS·ERR로 보여 줍니다.

H06 · LEARNER-OWNED PYTHON ACTION

조회 Action만 허용하기

Action은 Dialog Rail이 문장의 뜻을 고른 다음 부르는 Python 함수입니다. llm-security-control-plane/guided-labs/h06-nemo-action/actions.py의 Starter는 잔액 조회뿐 아니라 송금처럼 상태를 바꾸는 작업도 허용합니다. 허용목록을 조회 Action 하나로 줄입니다.

# 결과를 확인만 하는 Action 하나만 다음 단계로 보냅니다.
ALLOWED_ACTIONS = frozenset({"get_account_balance"})

이 한 줄은 송금 요청을 답변 문구로만 가리는 것이 아닙니다. 허용목록에 없는 Action은 합성 Provider를 호출하기 전에 멈춥니다. 정상 조회는 실제 Provider를 호출해야 하므로 모든 Action을 막는 구현도 통과하지 못합니다.

저장한 코드를 image에 넣고 H06 learner 서비스만 다시 연결합니다. 합성 Provider의 독립 ledger는 다시 만들지 않습니다.

docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  build guided-h06-nemo-action
docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  up -d --no-deps --force-recreate guided-h06-nemo-action
서버가 잔액 조회와 두 가지 송금 요청, 지원하지 않는 요청을 H06 NeMo 서비스에 보냅니다. 거부 문구만으로는 차단을 증명할 수 없습니다. 검증기는 Python Action event와 별도 합성 Provider의 호출·부작용 원장을 다시 확인해, 조회는 실행되고 송금은 Provider 전에 멈췄는지 HIT·PASS·ERR로 보여 줍니다.

Agent가 고른 모델·MCP Server·Tool은 실행 후보일 뿐 권한이 아닙니다. H21에서는 인증된 주체의 서버 정책으로 허용목록과 Tool 횟수·결과 크기·상태 소유자를 제한합니다.

독립 실행H21은 H01·H02·H22의 source, 상태와 AWS 자원을 사용하지 않습니다. 결정적 Provider fixture와 H21 전용 MCP Server 두 개로 downstream 호출 여부를 검증합니다.

LEARNER-OWNED AGENT POLICY

Agent의 연결 대상과 실행 예산 제한하기

guided-labs/h21-agent-policy/policy.py의 Starter는 요청이 제시한 model·server·Tool·한도를 그대로 사용합니다. 허용목록과 state owner를 검사하고 서버가 정한 두 상한만 반환하도록 authorize()를 완성합니다.

if model not in configured["models"]:
    raise PolicyDenied("model-not-allowed")
if server_id not in configured["servers"]:
    raise PolicyDenied("mcp-server-not-allowed")
if tool not in configured["tools"]:
    raise PolicyDenied("tool-not-allowed")
if state_owner != principal:
    raise PolicyDenied("state-owner-mismatch")

반환값의 max_tool_calls, max_result_bytes, tool_timeout_ms도 요청값이 아니라 정책값을 사용합니다. OAuth audience·scope는 MCP Server가 한 번 더 검사합니다.

docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  build guided-h21-host guided-h21-provider guided-h21-trusted-mcp guided-h21-untrusted-mcp
docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  up -d --no-deps --force-recreate guided-h21-provider guided-h21-trusted-mcp guided-h21-untrusted-mcp guided-h21-host
서버가 미리 준비한 아홉 가지 요청을 H21 Agent Host에 보냅니다. 허용하지 않은 모델·MCP Server·Tool과 한도를 넘는 요청은 뒤쪽 서비스에 닿기 전에 멈춰야 합니다. 실제 외부 작업은 하지 않고, 검증기가 각 요청의 흐름과 호출 횟수를 다시 대조합니다.

외부 문서의 문장이 모델에게 publish_notice Tool을 제안하게 했다고 가정합니다. 제안은 실행 허가가 아니므로 MCP Server가 requester·reviewer·Tool·인자·만료·nonce를 다시 검사하도록 만듭니다.

격리 안내실제 메일·삭제·결제 API는 호출하지 않습니다. 승인된 부작용은 H22 전용 SQLite에 훈련 공지 한 건만 기록합니다.

LEARNER-OWNED MCP SERVER

Tool 제안과 실행 권한 분리하기

guided-labs/h22-mcp-approval/server.py는 공식 SDK의 Streamable HTTP Server입니다. Starter는 요청마다 임의 nonce를 새로 만들어 승인 없는 호출도 실행합니다. publish_notice()에서 아래처럼 서버 검사를 연결합니다.

nonce = verify_approval(
    approval_token,
    suite_id,
    call_id,
    trace_id,
    requester,
    notice,
)

검사 뒤 SQLite transaction이 nonce 소비와 훈련 공지 기록을 함께 처리합니다. 그래서 다른 인자, 만료 Token과 같은 nonce 재사용은 공지를 만들기 전에 멈춥니다. Host의 승인과 실제 공지는 같은 trace_id에 묶입니다.

docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  build guided-h22-mcp-server guided-h22-host
docker compose \
  --env-file llm-security-control-plane/.state/guided-course.env \
  --file examples/security-monitoring/compose.guided.yaml \
  up -d --no-deps --force-recreate guided-h22-mcp-server guided-h22-host
서버가 승인이 없거나, 자신을 스스로 승인하거나, 승인 후 내용을 바꾸는 경우 등 여섯 가지 요청을 MCP Host와 Server에 보냅니다. 올바른 승인 한 번만 공지를 만들어야 하며, 외부 메일·삭제·결제는 실행하지 않습니다. 검증기가 전용 SQLite에 기록된 건수와 각 요청의 흐름을 대조합니다.
