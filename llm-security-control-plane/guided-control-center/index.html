직접 작성

여러 상담 앱이 같은 규칙으로 Nova Lite를 호출하도록 작은 Bedrock Gateway를 완성합니다. 제공된 서버는 인증과 실행 기록을 담당합니다. 여러분이 작성할 함수는 요청이 올바른지 검사하고, 출력 한도를 계산한 뒤 모델을 호출합니다. Starter는 아직 이 기능이 없으므로 501을 반환하며 모델을 호출하지 않습니다.

LEARNER-OWNED GATEWAY

HTTP 요청을 Nova Lite 호출로 연결하기

llm-security-control-plane/guided-labs/h01-bedrock-gateway/learner.py의 handle_request(body, client)를 작성합니다. body는 사용자가 보낸 JSON이고, client.converse()는 Boto3와 같은 방식으로 모델을 호출하는 제공 연결입니다. 인증 Token과 실행 기록은 수정하지 않습니다.

  • message와 max_output_tokens만 받습니다. 누락되거나 다른 필드가 있으면 거부합니다.
  • 메시지는 1~4,000자 문자열이어야 하며 공백만 있으면 거부합니다. 출력 요구는 1~512 정수만 받습니다. 문자열·실수·참/거짓 값은 정수가 아닙니다.
  • 잘못된 요청은 ValueError로 거부합니다. 서버가 이를 HTTP 422로 바꿉니다. 이때 모델을 호출하면 안 됩니다.
  • 정상 요청은 us.amazon.nova-lite-v1:0에 user text로 한 번 전달합니다. temperature는 0.0이며 입력 문장은 그대로 유지합니다.
  • 출력 요구가 128 이하면 그대로 쓰고, 더 크면 128로 제한합니다. 예를 들어 37은 37, 301은 128로 전달해야 합니다.
  • 실제 Converse 응답을 그대로 반환합니다. 답변이나 검증 결과를 직접 만들어 반환하지 않습니다.

P03 · LEARNER-OWNED SYNC APP

현재 동기화가 끝난 뒤에만 검색하기

고객지원 문서를 고쳤지만 검색용 정리는 아직 진행 중입니다. 정리가 끝나기 전에 검색하면 최신 문서를 확인했다고 믿기 어렵습니다. 동기화(ingestion)는 S3 원문을 Knowledge Base의 검색 저장소에 반영하는 작업입니다. P03은 P02·P11과 별도의 문서와 자원을 사용합니다.

guided-labs/h03-ingestion-search/learner.py의 async search_current(current_job_id, services)를 작성하세요. 제공된 await services.job_status()는 작업 번호인 ingestion_job_id와 상태인 status를 반환합니다. await services.retrieve()는 검색 결과를 반환합니다. 작업 번호·접속 주소·인증 정보는 실행 서버가 정합니다.

현재 번호와 같은 작업이 QUEUED·STARTING·IN_PROGRESS이면 검색하지 않고 {"status":"waiting","result":null}을 반환하세요. COMPLETE이면 검색을 한 번 호출하고 실제 응답을 {"status":"ready","result":검색 응답}에 담습니다. Python에서 JSON의 null은 None입니다.

작업 번호가 다르거나 빠진 경우, 상태가 없거나 잘못된 경우, FAILED·STOPPING·STOPPED이면 ValueError로 거부하세요. 상태 조회는 한 번만 수행하며 서비스 오류를 대기나 성공으로 바꾸지 않습니다. 코드를 작성한 뒤 P03 앱만 다시 빌드하고 연결하세요.

단독 검사에 사용한 Guardrail을 모델 호출에도 연결하기

DIALOG PATH + TOPICAL EVALUATION

정확한 연결과 안전한 답을 따로 확인하기

검증은 정확한 연락처 질문, 처음 보는 비슷한 표현, 복구 코드 요청, 지원하지 않는 요청을 차례로 보냅니다. 각 요청의 UserMessage → UserIntent → BotIntent → BotMessage event와 별도의 activated flow를 확인한 뒤 같은 설정으로 NeMo Topical 평가를 실행합니다.

NeMo 0.22.0의 이 평가는 UserIntent가 맞으면 BotIntent와 BotMessage도 맞다고 가정합니다. 따라서 0/0/0은 보류한 한국어 문장의 UserIntent 분류가 맞고 bot 오류 counter가 늘지 않았다는 뜻일 뿐, 실제 답을 확인한 안전 점수는 아닙니다. 실제 BotIntent·BotMessage와 합성 marker는 별도의 고정 네 요청이 판정합니다.

서버가 고정한 한국어 요청 네 개를 현재 P05 Dialog Rail에 보내 intent·flow·BotMessage를 기록한 뒤, 같은 설정으로 NeMo Topical 평가를 실행합니다. 검증기는 새 영수증과 평가 결과를 다시 확인해 정상 연락처는 유지되고 복구 코드 marker는 사라졌는지 HIT·PASS·ERR로 보여 줍니다.

tracer.start_as_current_span(name, attributes={...})은 with로 열고 닫는 기록 구간입니다. 열린 Span 안에 새 Span을 만들면 자식이 됩니다. 나중에 정해진 값은 span.set_attribute(key, value)로 기록하고, 실제 Trace ID는 span.get_span_context().trace_id에서 얻습니다. 정수를 32자리 소문자 16진수로 표시할 때는 format(value, "032x")를 사용할 수 있습니다.

contextlib.contextmanager는 yield가 한 번 있는 함수를 with에서 쓰게 해 줍니다. yield 앞뒤가 실제 단계의 시작·끝을 감쌉니다. 단계마다 업무 함수를 다시 호출하지 마세요. 안쪽 함수에서 바깥의 순번 변수를 갱신할 때는 nonlocal을 사용할 수 있습니다. JSON Log는 json.dumps()로 문자열을 만들어 logger.info(message)로 보내고, 건수는 counter.labels(decision=value).inc()로 늘립니다. 어떤 값과 순서로 연결할지는 직접 구현하세요.

  • Trace는 요청의 처리 경로입니다. security.request root Span 안에서 run_business(stage)를 한 번 실행하고, 반환값을 바꾸지 않고 돌려주세요.
  • stage(name)은 with로 여닫는 context manager입니다. 업무 함수가 이 구간에 들어올 때 같은 이름의 자식 Span을 만드세요. 자식에는 request_id와 1부터 연속된 정수 sequence를 기록합니다.
  • root에는 request_id, decision, stop_stage(정상은 빈 문자열), stage_count를 기록합니다. 요청 ID와 Trace ID는 Log·Trace를 묶는 표식입니다.
  • JSON Log는 요청마다 한 건입니다. request_id, trace_id, 실제 decision, stop_stage(정상은 null)를 담으세요. run_business의 반환값에는 결정·중단 단계·저장소 호출 수·결과가 있습니다.
  • Counter는 누적 처리 건수입니다. 제공된 counter의 decision label을 실제 결정에 맞춰 한 번 증가시키세요. 정상 1건·거부 2건이 각각 반영돼야 하며 요청 ID를 Metric label로 추가하지 않습니다.

SDK의 tracer·logger가 만든 Log·Trace는 Alloy를 거쳐 Loki·Tempo에 저장됩니다. Counter는 앱의 /metrics에서 Prometheus가 수집합니다. 실행 서버·업무 함수는 수정하지 않습니다. 신호 누락·중복, 가짜 단계, 업무 중복 호출, 반환값 변경은 미완료입니다.

Log의 decision·stop_stage, Span의 stage·sequence, closure의 closed·downstream_count를 확인하세요. sequence는 1부터 이어지는 정수입니다. 다른 요청은 제외하고, 같은 요청의 누락·중복·서로 다른 Trace·미종료 기록·호출 수 모순은 ValueError로 거부해야 합니다.

반환할 항목은 request_id, trace_id, decision, stages, stop_stage, downstream_count입니다. stages는 sequence 순서입니다. 정상은 allow와 stop_stage=null, 거부는 block과 실제 마지막 단계입니다. 차단 전에 발생한 저장소 호출이 있다면 0으로 바꾸지 않습니다. 웹에 판정값을 제출하는 것은 허용하지 않습니다.

수정 뒤 setup 작업 경로에서 P19만 다시 빌드·적용합니다. 제공 실행 골격과 검증기는 수정하지 않습니다.

docker compose --env-file llm-security-control-plane/.state/guided-course.env --file examples/security-monitoring/compose.guided.yaml build guided-h19-investigation
docker compose --env-file llm-security-control-plane/.state/guided-course.env --file examples/security-monitoring/compose.guided.yaml up -d --no-deps --force-recreate guided-h19-investigation
P19 서비스가 정상 조회·인가 거부·인증 거부를 처리하고 Loki·Tempo에서 기록을 가져옵니다. 작성한 함수를 기본·역순·손상된 사본 10개로 실행한 뒤 검증기가 원문과 대조합니다. 수집 장애나 함수 오류는 미완료이며 전체 LLM 보안을 증명하지는 않습니다.

P20 · ALERT + DASHBOARD

거부 요청을 알려주는 경보와 그래프 만들기

공지 조회 앱은 읽기만 허용된 사용자의 게시 요청을 거부합니다. 실제 거부 횟수를 보고 알림을 보내고, 정상 조회는 계속 처리되는지 그래프로 확인하려고 합니다. 다른 앱의 거부를 P20 경보에 섞으면 안 됩니다.

guided-labs/h20-alert-dashboard/rules.yaml과 dashboard.json 두 파일을 작성합니다. 요청 처리와 횟수 기록은 제공된 서버가 담당합니다. P17~P19의 코드나 실행 기록은 사용하지 않습니다.

  • guided_p20_decisions_total은 처리한 요청의 누적 횟수입니다. practice는 P20 또는 background, decision은 허용 allow 또는 거부 block입니다.
  • 최근 20초에 P20 거부 요청이 생긴 상태가 4초 지속되면 GuidedP20BlockedRequests 경보를 발생시키고, 거부가 더 없으면 해제합니다. 경보 label은 practice=P20, severity=warning을 유지합니다.
  • rules.yaml에는 groups 아래 경보 규칙 하나를 둡니다. dashboard.json의 UID guided-p20와 datasource UID p20을 유지하고 패널 하나의 target A에 조회문을 작성합니다. 조회 결과는 decision별 P20 누적 횟수 두 개여야 합니다.
  • 정상 조회와 다른 앱의 거부에는 경보가 없어야 합니다. P20 거부 뒤에는 대기 pending → 발생 firing → 해제 알림이 있어야 하며, 발생 중에도 정상 조회를 처리해야 합니다. 패널 수치는 실제 Counter와 비교합니다.

설정은 P20 전용 이미지에 포함됩니다. 수정한 두 파일을 적용할 때만 아래 세 서비스를 다시 빌드합니다. 검증 버튼은 빌드하거나 정답 설정을 넣어주지 않습니다.

docker compose --env-file llm-security-control-plane/.state/guided-course.env --file examples/security-monitoring/compose.guided.yaml build guided-h20-alerts guided-h20-prometheus guided-h20-grafana
docker compose --env-file llm-security-control-plane/.state/guided-course.env --file examples/security-monitoring/compose.guided.yaml up -d --no-deps --force-recreate guided-h20-alerts guided-h20-prometheus guided-h20-grafana
P20 서버에 정상 조회와 거부 요청을 보냅니다. 전용 Prometheus·Alertmanager·Grafana의 경보 발생·해제와 패널 수치를 독립 검증기가 다시 조회합니다. 설정 누락·시간 초과는 미완료이며, 공지 앱의 권한 거부를 확인하는 실습이지 LLM 공격 탐지 성능 시험은 아닙니다.

Agent가 고른 모델·MCP Server·Tool은 실행 후보일 뿐 권한이 아닙니다. P21에서는 인증된 주체의 서버 정책으로 허용목록과 Tool 횟수·결과 크기·상태 소유자를 제한합니다.

독립 실행P21은 P01·P02·P22의 source, 상태와 AWS 자원을 사용하지 않습니다. 결정적 Provider fixture와 P21 전용 MCP Server 두 개로 downstream 호출 여부를 검증합니다.

LEARNER-OWNED AGENT POLICY

Agent의 연결 대상과 실행 예산 제한하기

guided-labs/h21-agent-policy/policy.py의 Starter는 요청이 제시한 model·server·Tool·한도를 그대로 사용합니다. 허용목록과 state owner를 검사하고 서버가 정한 실행 상한만 반환하도록 authorize()를 완성합니다.

authorize()에서 모델·Server·Tool이 서버 허용목록에 있는지, 상태 소유자가 인증 주체와 같은지 확인하세요. 허용되지 않은 대상은 호출 전에 거부해야 하며 정상 제안→Tool→최종 응답 경로는 유지합니다.

반환값의 max_tool_calls, max_result_bytes, tool_timeout_ms도 요청값이 아니라 정책값을 사용합니다. OAuth audience·scope는 MCP Server가 한 번 더 검사합니다.

LEARNER-OWNED MCP SERVER

Tool 제안과 실행 권한 분리하기

guided-labs/h22-mcp-approval/server.py는 공식 SDK의 Streamable HTTP Server입니다. Starter는 요청마다 임의 nonce를 새로 만들어 승인 없는 호출도 실행합니다. publish_notice()에서 서버의 승인 검사를 연결합니다.

서명된 승인과 실제 요청의 주체·Tool·인자·실행 및 Trace를 대조하고 만료 여부를 확인하세요. 승인 없이 호출하거나 다른 인자로 바꾸면 공지가 생성되면 안 됩니다. 정확한 승인 한 번만 실행되고 같은 승인은 다시 사용할 수 없어야 합니다.

검사 뒤 SQLite transaction이 nonce 소비와 훈련 공지 기록을 함께 처리합니다. 그래서 다른 인자, 만료 Token과 같은 nonce 재사용은 공지를 만들기 전에 멈춥니다. Host의 승인과 실제 공지는 같은 trace_id에 묶입니다.
