# P22 UI + Starter 독립 풀이 감사

## 판정

**채점 가능한 완성 답 도출이 가능하다.**

Starter가 다음 필수 계약을 모두 제공한다.

- MCP Tool의 정확한 signature
- 승인 Token의 `encoded.signature` 형식
- HMAC-SHA256 검증 방식과 secret 출처
- 승인 claims와 exact-call digest 구성
- reviewer, server ID, Tool 이름, 만료와 nonce 검증 helper
- nonce와 effect의 SQLite schema
- `BEGIN IMMEDIATE` transaction
- 성공 반환 객체와 MCP `ToolError` 방식

핵심 수정은 `publish_notice()`가 매 요청마다 새 nonce를 만드는 취약 코드를 제거하고, `verify_approval(...)`이 반환한 서명된 nonce를 사용하는 것이다.

또한 Starter의 `verify_approval()`은 reviewer가 고정된 `course-reviewer`인지 검사하지만 requester도 `course-reviewer`인 자기 승인 사례를 별도로 거부하지 않는다. UI와 채점 설명이 자기 승인을 명시적으로 금지하므로 `claims["reviewer"] == requester`를 거부해야 한다.

## 완성 답

전체 Starter에서 `secrets` import를 제거하고 아래 두 함수를 사용한다. 다른 코드는 그대로 유지한다.

```python
def verify_approval(
    approval_token: str,
    suite_id: str,
    call_id: str,
    trace_id: str,
    requester: str,
    notice: str,
) -> str:
    claims = decode_token(approval_token)

    if claims.get("reviewer") == requester:
        raise ToolError("approval-self-review-forbidden")

    expected = {
        "suite_id": suite_id,
        "requester": requester,
        "reviewer": "course-reviewer",
        "server_id": SERVER_ID,
        "tool": "publish_notice",
        "args_sha256": canonical_digest(
            suite_id,
            call_id,
            trace_id,
            requester,
            notice,
        ),
    }
    if any(claims.get(key) != value for key, value in expected.items()):
        raise ToolError("approval-exact-call-mismatch")
    if int(claims.get("expires_at", 0)) <= int(time.time()):
        raise ToolError("approval-expired")
    nonce = claims.get("nonce")
    if not isinstance(nonce, str) or not nonce:
        raise ToolError("approval-nonce-invalid")
    return nonce


@mcp.tool()
def publish_notice(
    suite_id: str,
    call_id: str,
    trace_id: str,
    requester: str,
    notice: str,
    approval_token: str = "",
) -> dict:
    """Publish one local training notice after an exact-call approval."""
    nonce = verify_approval(
        approval_token,
        suite_id,
        call_id,
        trace_id,
        requester,
        notice,
    )

    try:
        with connect() as database:
            database.execute("BEGIN IMMEDIATE")
            database.execute(
                "INSERT INTO consumed VALUES(?,?)",
                (nonce, suite_id),
            )
            database.execute(
                "INSERT INTO effects(call_id,suite_id,notice,trace_id) VALUES(?,?,?,?)",
                (call_id, suite_id, notice, trace_id),
            )
            effects = database.execute(
                "SELECT COUNT(*) FROM effects WHERE suite_id=?",
                (suite_id,),
            ).fetchone()[0]
    except sqlite3.IntegrityError as exc:
        raise ToolError("approval-already-consumed") from exc

    return {
        "decision": "allow",
        "suite_id": suite_id,
        "call_id": call_id,
        "trace_id": trace_id,
        "effects": effects,
        "external_action_called": False,
    }
```

## 요구사항과의 대응

### 승인 없는 호출

기본값 `approval_token=""`은 `decode_token()`에서 `approval-token-missing` ToolError를 일으킨다. DB transaction 전에 실패하므로 nonce와 effect가 기록되지 않는다.

### 서명 변조

`decode_token()`이 HMAC-SHA256을 `compare_digest`로 검사한다. 서명이 맞지 않으면 claims를 신뢰하기 전에 중단한다.

### 자기 승인

서명된 claims의 reviewer와 실제 함수의 requester가 같으면 `approval-self-review-forbidden`으로 중단한다. 고정 reviewer `course-reviewer` 검증도 기존 expected 비교로 유지된다.

### Tool·주체·인자·trace 변경

`expected`가 다음 값을 모두 서명 claims와 대조한다.

- `suite_id`
- `requester`
- `reviewer`
- `server_id`
- `tool`
- `args_sha256`

`args_sha256`에는 `suite_id`, `call_id`, `trace_id`, `requester`, `notice`가 canonical JSON으로 들어간다. 따라서 공지 내용, 실행 ID, trace 또는 주체를 바꾸면 exact-call mismatch로 transaction 전에 멈춘다.

### 만료 승인

`expires_at <= int(time.time())`이면 transaction 전에 `approval-expired`가 발생한다.

### nonce 재사용

서명된 nonce를 `consumed.nonce` primary key에 insert한다. 같은 승인을 재사용하면 SQLite `IntegrityError`가 발생하고 `approval-already-consumed` ToolError로 바뀐다.

### 원자적 부작용

`BEGIN IMMEDIATE` transaction 안에서 consumed insert가 먼저, effects insert가 다음에 실행된다. nonce 충돌이나 effect insert 실패 시 context manager가 transaction을 rollback하므로 nonce 소비와 공지 생성이 함께 성공하거나 함께 실패한다.

### 외부 부작용 없음

수정된 함수는 Starter와 마찬가지로 P22 SQLite에만 insert하며 반환값도 `external_action_called: False`를 유지한다.

## 남은 누락 또는 모호성

채점기의 여섯 사례를 통과하는 구현을 막는 누락은 없다. 다만 실제 보안 의미에는 다음 제한이 남는다.

### requester의 신뢰 가능한 인증 출처

`requester`는 MCP Tool의 문자열 인자다. Starter에는 MCP 인증 context에서 서버가 검증한 실제 주체를 읽는 코드가 없다. 따라서 이 구현이 확인하는 것은 다음 두 값의 일치다.

- Tool 호출 인자로 들어온 `requester`
- 서명된 승인 claims의 `requester`

서명 Token을 만들 수 없는 공격자는 claims를 변조할 수 없지만, 다른 사용자의 유효한 Token과 그 Token에 적힌 requester 문자열을 함께 재전송하는 상황을 서버 인증 주체와 대조할 수는 없다. UI의 “실제 요청의 주체”를 엄격한 authenticated principal로 해석하면 Starter에 다음이 추가로 필요하다.

- MCP 인증 context에서 requester를 얻는 API
- Tool 인자의 requester를 제거하거나 context requester와 대조하는 코드

제공된 여섯 채점 사례가 Host가 전달한 requester와 서명 claim의 대조를 의미한다면 위 완성 답으로 충분하다. 강한 실제 인증 경계를 요구한다면 Starter만으로는 그 부분을 구현할 수 없다.

### 자기 승인 오류 문구

UI는 자기 승인을 `ToolError`로 거부하라고 요구하지만 exact 메시지는 지정하지 않는다. `approval-self-review-forbidden`은 기존 오류 naming style에 맞춘 구현 자유도다. 채점기가 DB side effect와 흐름만 검사한다면 결과에 영향이 없다. 오류 문자열까지 exact match한다면 기대 문자열을 UI에 추가해야 한다.

### malformed Token payload 오류

잘못된 base64 또는 JSON은 Python decoding exception으로 전달될 수 있다. UI는 오류를 성공으로 처리하지 말라고 했으므로 부작용 없이 실패한다는 점은 만족한다. 모든 malformed Token을 반드시 `ToolError`로 정규화해야 한다는 조건은 없다.

## 최종 결론

UI와 Starter만으로 채점용 완성 답을 작성할 수 있다. 임의 nonce를 서명 검증에서 얻은 nonce로 교체하고 자기 승인을 명시적으로 거부하면, exact-call 검증 뒤 같은 SQLite transaction에서 nonce 소비와 공지 한 건 생성을 원자적으로 처리한다.
