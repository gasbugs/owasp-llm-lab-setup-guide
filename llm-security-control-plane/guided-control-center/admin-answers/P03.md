# P03 최종 UI + Starter 감사

## 판정

**완성 답 도출이 가능하다.**

보강된 UI와 Starter가 다음 계약을 모두 제공한다.

- 정확한 함수 signature: `async search_current(current_job_id, aws)`
- `load_aws_session`과 `Config`의 import
- session, binding 및 config 생성 코드
- binding의 필수 key 세 개
- 생성할 두 Boto3 client와 리전·config
- ingestion 조회 호출과 응답에서 확인할 ID·상태
- waiting, ready 및 오류 상태의 처리
- retrieve의 전체 인자와 반환 형태
- Boto3 메서드는 동기 호출하며 SDK 오류를 그대로 전달한다는 조건
- `current_job_id`는 AWS ingestion ID가 아닌 채점용 번호라는 구분

따라서 placeholder나 외부 정보 없이 전체 파일을 작성할 수 있다.

## 완성 답 전체

```python
from aws_auth import load_aws_session
from botocore.config import Config


async def search_current(current_job_id, aws):
    session, binding = load_aws_session(aws)
    config = Config(
        connect_timeout=5,
        read_timeout=20,
        retries={"total_max_attempts": 1},
    )

    required_binding_keys = {
        "knowledgeBaseId",
        "dataSourceId",
        "ingestionJobId",
    }
    if not isinstance(binding, dict) or not required_binding_keys.issubset(binding):
        raise ValueError("Missing ingestion binding")

    agent = session.client(
        "bedrock-agent",
        region_name="us-east-1",
        config=config,
    )
    runtime = session.client(
        "bedrock-agent-runtime",
        region_name="us-east-1",
        config=config,
    )

    response = agent.get_ingestion_job(**binding)
    if not isinstance(response, dict):
        raise ValueError("Invalid ingestion response")

    ingestion_job = response.get("ingestionJob")
    if not isinstance(ingestion_job, dict):
        raise ValueError("Missing ingestion job")

    ingestion_job_id = ingestion_job.get("ingestionJobId")
    if ingestion_job_id is None:
        raise ValueError("Missing ingestion job ID")
    if ingestion_job_id != binding["ingestionJobId"]:
        raise ValueError("Ingestion job ID mismatch")

    status = ingestion_job.get("status")
    if not isinstance(status, str):
        raise ValueError("Invalid ingestion status")

    if status in {"QUEUED", "STARTING", "IN_PROGRESS"}:
        return {"status": "waiting", "result": None}

    if status != "COMPLETE":
        raise ValueError("Ingestion did not complete")

    result = runtime.retrieve(
        knowledgeBaseId=binding["knowledgeBaseId"],
        retrievalQuery={"text": aws.query},
        retrievalConfiguration={
            "vectorSearchConfiguration": {
                "numberOfResults": 3,
            }
        },
    )
    return {"status": "ready", "result": result}
```

## 요구사항과의 대응

### binding 검증

`load_aws_session(aws)` 직후 `knowledgeBaseId`, `dataSourceId`, `ingestionJobId` 세 key가 모두 있는지 검사한다. `binding` 자체가 dict가 아닌 경우도 `ValueError`로 처리해 Boto3 호출 전에 중단한다.

### Client 생성

다음 두 client를 정확한 서비스명으로 만든다.

- `bedrock-agent`
- `bedrock-agent-runtime`

둘 다 `region_name="us-east-1"`과 Starter의 `config`를 전달한다.

### 현재 ingestion 확인

`agent.get_ingestion_job(**binding)`을 한 번만 호출한다. 응답과 `ingestionJob` 구조를 검사한 뒤 응답의 `ingestionJobId`가 binding의 AWS ingestion ID와 같은지 확인한다.

`current_job_id`는 UI가 AWS 작업 ID와 구분한 채점용 작업 번호이므로 AWS API 인자나 ID 대조에 사용하지 않는다.

### 상태 처리

- `QUEUED`, `STARTING`, `IN_PROGRESS`: retrieve를 호출하지 않고 waiting 반환
- `COMPLETE`: retrieve를 정확히 한 번 호출
- `FAILED`, `STOPPING`, `STOPPED`: `status != "COMPLETE"` 분기에서 `ValueError`
- 그 밖의 알 수 없는 문자열 상태: 정상 또는 waiting으로 오인하지 않고 `ValueError`
- 상태 누락 및 문자열이 아닌 상태: 명시적인 `ValueError`

### 검색 요청

검색은 `COMPLETE` 분기에서만 실행하며 UI가 지정한 값을 그대로 사용한다.

```python
runtime.retrieve(
    knowledgeBaseId=binding["knowledgeBaseId"],
    retrievalQuery={"text": aws.query},
    retrievalConfiguration={
        "vectorSearchConfiguration": {"numberOfResults": 3}
    },
)
```

SDK 응답을 수정하거나 일부만 추출하지 않고 `result`에 그대로 담는다.

### 오류 전달과 호출 방식

Boto3의 `get_ingestion_job`과 `retrieve`에는 `await`를 붙이지 않는다. `try`/`except`로 SDK 오류를 waiting이나 ready 응답으로 바꾸지 않으므로 오류가 그대로 전달된다. 반복 조회도 하지 않는다.

## 남은 누락 또는 모호성

채점 가능한 답을 막는 누락은 없다.

### `current_job_id`의 미사용

함수 parameter인데 사용하지 않는 점은 의도적이다. UI가 이를 “채점용 작업 번호”라고 설명하고 AWS 작업 ID는 `binding["ingestionJobId"]`라고 명시한다. 따라서 함수 내부에서 두 값을 비교하거나 AWS API에 `current_job_id`를 전달하면 오히려 잘못된 구현이다.

### 알 수 없는 상태 문자열

UI가 waiting 세 상태와 ready 한 상태를 허용하고 실패·중지 세 상태를 `ValueError`로 지정한다. 그 밖의 문자열 상태에 대한 별도 성공 동작은 없으므로 fail-closed 방식으로 `ValueError`를 내는 것이 자연스럽고 안전하다.

### binding 값의 자료형

UI는 필수 key의 존재를 요구하지만 값의 자료형 검증까지 요구하지 않는다. 위 답은 key 존재를 검사하고 값은 제공 인증 골격의 신뢰된 binding으로 사용한다. 값이 잘못돼 Boto3가 오류를 내면 SDK 오류를 그대로 전달한다는 조건과도 맞는다.

## 최종 결론

보강된 UI와 정확한 Starter만으로 P03의 전체 답을 명확히 작성할 수 있다. 위 구현은 ingestion 상태가 `COMPLETE`일 때만 검색하고, 대기 상태에서는 검색하지 않으며, 손상·실패 상태를 `ValueError`로 거부한다.
