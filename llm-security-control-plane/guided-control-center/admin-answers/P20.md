# P20 UI+Starter 최종 독립 감사

## 판정

**두 파일의 완성 답을 정확히 작성할 수 있다.**

보강된 UI는 기존 구조를 유지하고 `rules.yaml`의 `expr`·`for`, `dashboard.json` target A의 `expr`만 바꾸라고 명시한다. 두 Starter가 모두 제공되므로 보존할 UID, datasource, panel, group, rule과 labels가 확정된다.

## 완성된 `rules.yaml`

```yaml
# CUSTOM FILE: P20 learner Starter
# Format: https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/ · Apache-2.0
groups:
  - name: p20
    rules:
      - alert: GuidedP20BlockedRequests
        expr: increase(guided_p20_decisions_total{practice="P20", decision="block"}[20s]) > 0
        for: 4s
        labels: {severity: warning, practice: P20}
```

## 완성된 `dashboard.json`

```json
{
  "_comment": "CUSTOM FILE; Grafana dashboard model https://grafana.com/docs/grafana/latest/dashboards/build-dashboards/view-dashboard-json-model/; AGPL-3.0",
  "uid": "guided-p20",
  "title": "P20 요청 처리 건수",
  "schemaVersion": 41,
  "panels": [{
    "id": 1,
    "type": "timeseries",
    "title": "P20 허용·거부",
    "gridPos": {"x": 0, "y": 0, "w": 24, "h": 8},
    "datasource": {"type": "prometheus", "uid": "p20"},
    "targets": [{"refId": "A", "expr": "sum by (decision) (guided_p20_decisions_total{practice=\"P20\"})", "legendFormat": "{{decision}}"}]
  }]
}
```

## 답의 근거

- `increase(...[20s]) > 0`은 최근 20초 동안 P20 block counter가 증가했는지를 검사한다.
- `for: 4s`는 조건이 4초 유지된 뒤 firing되게 한다.
- alert selector가 `practice="P20"`, `decision="block"`을 모두 고정하므로 P20 allow와 background block은 경보에 포함되지 않는다.
- 새로운 P20 block이 없으면 마지막 증가가 20초 조회창 밖으로 나가 expression이 false가 되고 경보가 해제된다.
- `sum by (decision)`은 scrape 관련 label을 제거하고 P20 누적 counter를 allow와 block, decision별 두 결과로 만든다.
- Dashboard query는 증가량이나 비율이 아니라 UI가 요구한 실제 누적 Counter 값을 반환한다.
- 두 Starter의 나머지 구조와 값은 모두 그대로 유지한다.

## 남은 누락

구성 파일을 완성하는 데 필요한 조건은 없다.

Prometheus evaluation interval과 Alertmanager의 resolved 알림 전달 설정은 Starter 밖에서 제공되는 실행 환경에 속한다. 실제 pending → firing → resolved 전이와 Dashboard 수치는 세 서비스를 빌드·재생성한 뒤 검증해야 한다. 이는 답 구성의 누락이 아니라 실행 검증 단계다.
