# P18 최종 UI + Starter 독립 감사

## 판정

**완성 답을 정확히 도출할 수 있다.**

UI와 Starter가 다음 계약을 모두 제공한다.

- YAML의 정확한 top-level key: `logql`, `promql`, `trace_lookup`
- Loki stream의 정확한 service label과 값
- 로그가 JSON이며 request·trace field 이름이 무엇인지
- 현재 실행 placeholder인 `{request_id}`와 `{trace_id}`
- Tempo lookup을 실행하게 하는 정확한 특별 값 `exact_trace_id`
- Prometheus metric 이름과 `hands_on`, `decision` labels
- 결과가 allow·block 두 decision별 누적값이어야 한다는 조건

## 완성 답 전체

```yaml
# CUSTOM FILE
# Query languages: LogQL, Tempo trace lookup, PromQL. License: project-authored.
logql: '{service_name="guided-h18-queries"} | json | request_id="{request_id}" | trace_id="{trace_id}"'
promql: 'sum by (decision) (guided_security_decisions_total{hands_on="H18", decision=~"allow|block"})'
trace_lookup: exact_trace_id
```

## 요구사항과의 대응

### LogQL

```logql
{service_name="guided-h18-queries"} | json | request_id="{request_id}" | trace_id="{trace_id}"
```

- `{service_name="guided-h18-queries"}`로 P18 서비스 stream만 선택한다.
- `| json`으로 JSON Log의 field를 추출한다.
- `request_id="{request_id}"`로 현재 요청만 남긴다.
- `trace_id="{trace_id}"`도 함께 일치시켜 같은 요청과 Trace의 기록만 반환한다.
- decision이나 policy rule을 query에 고정하지 않으므로 허용·거부 요청 모두 같은 조회문으로 실제 값을 확인할 수 있다.
- 주소, 시간창 또는 고정 숫자를 넣지 않는다.

### Tempo lookup

```yaml
trace_lookup: exact_trace_id
```

UI가 값 자체를 `exact_trace_id`로 두라고 명시한다. 실행기가 현재 서버 발급 Trace ID를 Tempo에 전달하므로 사용자가 `{trace_id}`를 직접 query 문자열로 조립할 필요가 없다.

### PromQL

```promql
sum by (decision) (
  guided_security_decisions_total{
    hands_on="H18",
    decision=~"allow|block"
  }
)
```

- 정확한 counter `guided_security_decisions_total`을 조회한다.
- `hands_on="H18"`로 P18 신호만 선택한다.
- `decision=~"allow|block"`으로 요구된 두 결과만 선택한다.
- `sum by (decision)`으로 instance나 process 등 다른 label이 있더라도 decision별 누적 건수 하나씩 반환한다.
- request ID를 metric label로 사용하지 않는다.
- `increase(...)`나 고정 숫자를 넣지 않고 누적 counter를 조회하므로 실행기가 전후 값을 비교해 allow·block이 각각 1 증가했는지 확인할 수 있다.

## 남은 누락 또는 모호성

채점 가능한 답을 막는 누락은 없다.

### LogQL에서 두 ID를 모두 쓰는 이유

고유한 request ID만으로도 요청을 좁힐 수 있지만 UI는 JSON Log에 request ID와 trace ID가 모두 있고 두 placeholder를 현재 실행 값으로 바꾼다고 명시한다. 둘을 함께 필터하면 다른 요청 혼입과 잘못 연결된 trace를 query 단계에서 모두 제외할 수 있다.

### PromQL의 명시적 decision filter

현재 metric에 allow와 block만 존재한다면 filter 없이 `sum by (decision)`해도 같은 결과가 나올 수 있다. 그러나 UI는 allow·block 두 누적 건수를 요구하므로 regex filter로 두 값만 명시하는 편이 계약을 정확히 표현한다.

### YAML key 순서

Starter의 key 순서를 유지했다. YAML mapping의 의미상 순서는 중요하지 않지만 원본 형식을 보존하므로 별도 해석이 필요 없다.

## 최종 결론

보강된 UI와 Starter만으로 P18의 전체 YAML을 완결할 수 있다. 위 답은 같은 request·trace의 JSON Log, 서버 발급 exact Trace, H18 allow·block counter를 실제 제품에서 조회하도록 구성한다.
