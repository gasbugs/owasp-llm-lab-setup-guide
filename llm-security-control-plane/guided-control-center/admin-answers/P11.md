# P11 UI + Starter 최종 독립 감사

## 판정

**가능**하다. 제한된 UI와 Starter만으로 채점 가능한 완성 답을 정확히 도출할 수 있다.

UI가 다음 네 필터 조건을 정확히 지정한다.

1. 문서 tenant가 인증된 `principal["tenant"]`와 같다.
2. 문서 `approval_status`가 정확히 `"approved"`다.
3. 문서 `source_kind`가 정확히 `"reviewed-handbook"`다.
4. 인증된 `principal["roles"]`와 문서 `allowed_roles`가 하나 이상 겹친다.

Browser가 전달한 `client_claims`의 `tenant`, `roles`, `require_approved`는 모두 무시해야 한다.

## 전체 완성 답

```python
"""Learner-owned H11 candidate filter using authenticated server values."""


def allowed_documents(
    principal: dict,
    documents: list[dict],
    client_claims: dict,
) -> list[dict]:
    roles = set(principal["roles"])

    return [
        document
        for document in documents
        if document["tenant"] == principal["tenant"]
        and document["approval_status"] == "approved"
        and document["source_kind"] == "reviewed-handbook"
        and bool(roles.intersection(document["allowed_roles"]))
    ]
```

`client_claims`는 기존 호출 인터페이스를 유지하기 위해 인자로 남지만 권한 결정에는 사용하지 않는다.

## 조건 충족 확인

- client가 tenant를 위조해도 필터는 인증 principal의 tenant만 사용한다.
- client가 roles를 위조해도 인증 principal의 roles만 사용한다.
- client가 `require_approved=false`를 보내도 승인되지 않은 문서는 제외한다.
- 승인 문서라도 `reviewed-handbook` 출처가 아니면 제외한다.
- 역할 교집합이 비어 있으면 제외한다.
- 모든 조건을 충족한 정상 문서는 입력 순서를 유지한 채 반환된다.
- 필터 결과만 다음 vector 검색으로 전달되므로 forbidden 문서는 cosine 점수 계산 후보에 들어가지 않는다.

## 남은 누락과 경미한 해석 여지

채점 가능한 핵심 구현에 필요한 조건은 누락되지 않았다.

- `client_claims`를 `_ = client_claims`로 명시적으로 소비할지는 코드 스타일 차이일 뿐 동작은 같다.
- `bool(...)` 없이 set intersection 자체의 truthiness를 사용해도 결과가 같다.
- 필드 누락·잘못된 타입에서 `KeyError` 또는 `TypeError`를 그대로 낼지 별도 오류로 바꿀지는 UI가 정하지 않았다. 제공 schema를 전제로 한 네 필터 조건에는 영향을 주지 않는다.
- role 문자열의 대소문자 정규화는 요구되지 않았으므로 저장된 값을 exact 비교한다.
